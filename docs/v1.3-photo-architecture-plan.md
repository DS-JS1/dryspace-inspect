# v1.3 — Photo & Media Architecture Plan

**Status:** Planning complete, build not started
**Supersedes:** `site-inspection-photo-upload-spec.md` (original brief)
**Target:** App v1.3 · Form 4.3 · schema 4
**Written:** 14 August 2026

---

## 1. The problem being solved

Full-resolution photos are being lost. The loss happens at handover: the protocol
in `03_Handover and Version Control Protocol` correctly instructs staff to delete
their device copy after exporting — but the exported artefacts do not carry the
originals.

| Artefact | Carries media? |
|---|---|
| Report `.html` | 1600px compressed copies only |
| Draft `.json` | Photos as data URLs, no video, warns over 20 MB |
| Backup `.json` | Nothing — field data only |

So once the device copy is deleted, the only surviving image of any photo is a
1600px re-encode embedded in a report. Originals are gone, and with them any
chance of using the photos as warranty or dispute evidence.

---

## 2. Decisions locked

These are settled. Do not relitigate in a later session without a stated reason.

| # | Decision | Rationale |
|---|---|---|
| D1 | **SharePoint** is the primary media store, via Microsoft Graph | Existing M365 licences and identities; handover files already live there; durable per-file links; no second cloud |
| D2 | **Per-user sign-in, no backend** (MSAL.js + PKCE) | No secret to hold, so no server to build or host. App stays static on GitHub Pages. Uploads attributed to the real person |
| D3 | **Three renditions** per photo: thumbnail 240px / report 1600px / untouched original | Keeps reports emailable (existing behaviour) while preserving evidence-grade originals |
| D4 | **Purge local original only after verified upload**, never automatically | Mirrors the existing "one baton, never a copy" rule |
| D5 | **Google Photos = secondary backup only**, fed from SharePoint, out of scope for v1.3 | Decoupled from the field path; can be built later without reopening the PWA |
| D6 | **Deferred upload queue**, not upload-on-tap | Basements have no signal. Upload drains when connectivity returns |
| D7 | **Native Camera app, then import** — not in-browser capture | Camera roll acts as an independent backup; preserves EXIF GPS for Google Photos Maps |
| D8 | Address labelling comes from the **form**, never GPS reverse-geocoding | Carried forward from the original spec — GPS is unreliable between adjacent properties |

### Corrections to the original spec

- **Upload-on-tap cannot work.** The original flow assumed a synchronous
  PWA → backend → Google upload at the moment of capture. That fails in every
  basement. Replaced by the deferred queue (D6).
- **Google Photos cannot supply durable per-photo links.** `baseUrl` expires in
  about an hour; `productUrl` requires the viewer to already have Photos access.
  The form would fill with dead links. SharePoint gives stable item IDs and URLs.
- **No backend is required.** The backend in the original spec existed mainly to
  hold Google's credentials. Per-user auth removes the need entirely (D2).
- **Do not compress video client-side.** Browser video compression is unreliable
  on iOS Safari. Queue video for wifi-only upload instead — less code, fewer
  failure modes.

## 3. Architecture

```
Native Camera app
      │  (photo lands in camera roll — backup copy #1)
      ▼
PWA file picker ──► IndexedDB ──► upload queue ──► SharePoint ──► link written
                    3 renditions   (drains on      (verified)     back to record
                                    connectivity)
                                                        │
                                                        ▼
                                            [later, separate project]
                                            scheduled sync ──► Google Photos
```

### Storage layout

```
/Site Inspections/
  INS-042 — 12 Marine Parade Kirra/
    INS-042_2026-08-14_s4-moisture-walls_001.jpg
    INS-042_2026-08-14_s4-moisture-walls_002.jpg
    INS-042_2026-08-14_s3a-access-route_001.jpg
```

Address lives in the **folder** (readable, browsable); inspection number, date,
field id and sequence live in the **filename**. This satisfies the original
spec's "not a generic camera filename" requirement while keeping paths short —
SharePoint has a ~400 character full-path limit.

Sanitise both: SharePoint bans `" * : < > ? / \ |` and addresses routinely
contain `/` (e.g. "Unit 3/12 Marine Pde"). The existing `slug()` helper covers
most of this but needs extending for the folder case.

### Upload mechanics

- Files **under 4 MB**: single `PUT` to the item content endpoint.
- Files **over 4 MB** (most full-res photos, all video): **resumable upload
  session**. Store the session URL on the media record so a dropped connection
  resumes from the break rather than restarting. Sessions stay valid ~7 days,
  so a drive home finishes what a basement started.

## 4. Verification — the guarantee before any deletion

Never trust the upload call's own response. A `200` can be returned on a
truncated upload.

**Tier 1 — independent re-read (baseline, ships in v1.3).**
After upload, issue a *separate* metadata request for the file. Confirm the
exact byte size matches and the item sits at the expected path. Record the
returned item ID and eTag on the media record. Catches truncation, interruption
and wrong-folder writes.

**Tier 2 — content hash (recommended).**
Graph returns `quickXorHash` for SharePoint files. Compute the same hash locally
and compare. True content verification rather than size-matching. Roughly 40
lines of JavaScript.

**Tier 3 — policy (costs nothing).**
- Purging is never automatic and never shares an operation with uploading.
- A "Reclaim space" action offers **only verified files**, after a 7-day grace
  period: *"47 photos across 3 inspections are verified in SharePoint. Free 180 MB?"*
- **Handover is hard-blocked** while any media on the record is unverified.

### Media record states

```
local ──► queued ──► uploading ──► uploaded (verified) ──► purged
                          │
                          └──► failed (retry, surfaced in UI)
```

Deletion only ever operates on records in `uploaded`. Because the camera roll
holds an independent copy throughout, no single failure at any state loses a photo.

## 5. Bugs to fix in the same pass

**B1 — Media records are keyed by DOM element id.**
`app/index.html:2076` stores `field: input.id`. This is the exact fragility that
v1.2 eliminated everywhere else by introducing `data-fid` — rename a file
input's `id` and its photos orphan silently. Fix with a stable `data-mfid` and
migrate existing records.

**B2 — Draft import does not dedupe.**
`importDraftMedia` assigns a fresh `mid` to every incoming file with no
existence check, so importing the same draft twice silently duplicates every
photo. Moving drafts to carry *links* instead of embedded data URLs fixes this
and collapses the 20 MB draft-size problem at the same time.

**B3 — EXIF is stripped today.**
The current canvas re-encode discards all EXIF including GPS. Uploading the
untouched original preserves it — required if Google Photos Maps is ever to work.

---

**B4 — Retired dropdown's "Other" option has no value rule.** *(found by tests, Batch 0)*
The v1.1.1 "Basement construction type" dropdown had 6 options. `VALUE_RULES`
converts 5 of them into ticked checkboxes; `Other` has none. A record that chose
`Other` **and** typed a description is fine — the merge rule carries it. A record
that chose `Other` and left the description blank ticks nothing, so the merged
wall-construction field reads blank where the original said "Other".

No data is destroyed (the answer is preserved under `unmapped:`), but it is
invisible in the form. The fix is not a one-liner: the target checkbox already
carries a `data-legacy` attribute for the checkbox-list migration and an element
can hold only one, so `assignKeys()` needs to accept multiple rules per element
or the rule must be declared explicitly in code.

**Renditions moved to Batch 2 — deliberately.** Storing untouched originals is
only useful once there is somewhere to send them. Shipping rendition capture
before the upload path exists would fill iPad storage with full-resolution photos
that have no way off the device, making storage pressure *worse* than today
rather than better. Originals and the upload queue belong in the same release.

### Batch 2 — Renditions, auth, upload queue, verification · **HIGH effort** · large
- [ ] Three-rendition capture: thumb 240 / report 1600 / untouched original
- [ ] Storage quota warnings as originals accumulate
- [ ] Media state machine (`local` → `queued` → `uploaded` → `purged`)
- [ ] Entra ID app registration (free); tenant admin consent
- [ ] MSAL.js PKCE sign-in, token cached and refreshed
- [ ] Deferred upload queue with retry and resumable sessions
- [ ] Metadata-driven folder + filename generation, sanitised
- [ ] Tier 1 verification (independent re-read)
- [ ] Tier 2 verification (quickXorHash)
- [ ] Per-photo upload status in the UI
- [ ] Durable links written back into the record

Build as a self-contained module (`ds-media-sync.js`) so the planned job-update
and silica-worksheet PWAs can reuse it — per the original spec's reusability note.

This matters more than a nice-to-have: the stated trajectory is several PWAs
built separately, then merged into a single native app once each works live.
Anything written as bespoke form logic here has to be untangled at that merge.
Anything written as a module moves across intact. Batch 2 is the first real
chance to set that pattern, and the media layer is the right thing to set it with
— it is the piece every one of those apps will need.

**This is where most of the token budget goes** — likely more than the other
four batches combined.

## 8. Out of scope for v1.3

- **Google Photos secondary backup.** Server-side scheduled sync reading from
  SharePoint. No first-party Power Automate connector exists for Photos, so this
  needs a custom connector or small script. Note that full-res originals consume
  Google account storage — size this before committing.
- **Analytics database.** The original spec's cross-job querying ("every job with
  a leaking wall-floor junction") needs a structured backend database. Real
  eventual need, but building it now would stall the fix that is actually hurting.
- **Video compression.** See §2 corrections.
