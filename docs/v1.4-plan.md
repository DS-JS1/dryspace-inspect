## 2. Confirmed bugs

### B5 — an interrupted upload strands the record permanently ☑ FIXED in v1.3.1

**This is almost certainly the cause of "the Upload now button disappears and I
cannot get it back."**

`pendingUploads()` in `index.html` counts `local`, `queued` and retryable
`failed`. It does **not** count `uploading`. And nothing at start-up resets an
interrupted upload.

So: the app is killed or backgrounded mid-upload → the record stays `uploading`
forever → it is invisible to both the queue and the button → the photo never
uploads and nothing says so.

**Fix:** on start-up, move every record in `uploading` back to `queued` — it was
interrupted by definition, since nothing can still be in flight after a reload.
`DSMedia.setState` currently forbids `uploading → queued`, so the transition
table needs it, or use an explicit `recoverInterrupted()`.

**Add a test:** a record left in `uploading` must be recovered on the next start.

> **Done — v1.3.1.** `DSMedia.recoverInterrupted()` runs at start-up, before the
> queue is built. The transition table was *not* widened: `uploading → queued`
> stays illegal so a record cannot move backwards mid-drain (D28). A record that
> has already used its attempts is marked failed and flagged for attention rather
> than returned to a queue that would skip it — that would be the same
> invisibility by another route. Reproduced and verified against the running app:
> before the fix `pendingUploads()` and `stuckUploads()` both returned 0 for a
> stranded record; after a reload it is `queued` and the button is back.

### B6 — the queue has no timeout ☑ FIXED in v1.3.1

If a request hangs, the app sits at *"Uploading…"* indefinitely with no feedback
and no way out. There is no per-file status on screen either, so there is nothing
to read when it stalls.

**Fix:** a request timeout in `ds-sharepoint.js` (AbortController), per-file state
visible in the UI, and the failure reason surfaced rather than logged.

> **Done — v1.3.1.** All three. 60s on metadata, folder creation and
> verification; 180s on an upload. The chunked PUT carries its own deadline
> because it bypasses `call()` and is the request most likely to stall on a phone
> — which matters directly for §3 hypothesis 1. A timeout is classified as
> temporary, so the queue retries rather than holding a good photo back (D29).
> The sync bar now lists every unfinished file with its state, percentage while
> in flight, and the real reason on failure (D30).

### B7 — everything except photos bypasses SharePoint ☑ FIXED in Batch 2

*Send Report*, *Share Photos and Video Files*, *Share Draft*, *Print PDF* all use
`navigator.share`, which offers WhatsApp and Mail on a phone. On desktop it
appears to work only because the SharePoint folder is a synced drive.

This is the architectural gap. See §4.

> **Done in Batch 2.** *Hand over through SharePoint* uploads the record to
> `current/` and files the previous version in `archive/`. The share sheet
> survives, explicitly labelled as the offline fallback — which is the one case
> it was always the right tool for.

### B8 — Import Draft reads the device, not SharePoint ☑ FIXED in Batch 2

`importFile()` uses a local file input. Handing the baton **on** works from a PC;
picking it **up** does not work anywhere. See §4.

> **Done in Batch 2.** *Take over an inspection from SharePoint* lists every
> inspection with a file waiting in `current/` and brings the chosen one down.
> Nobody has to send anybody anything.

## 3. The mobile hang — ranked hypotheses

Do not guess. Add the diagnostics in B6 first, reproduce, and read the answer.
That said, the strongest candidate is listed first for a reason.

> **Read this before the list.** Three of the four were addressed in v1.3.2 by
> reading the code, and **none of them is confirmed as the mobile fault.** Each
> was a real defect capable of producing the symptom; the cause is still unproven.
> Run `diagnostics.html` on the failing device to find out which — it names the
> hypothesis when it confirms one.
>
> **The tenant was inspected on 18 Aug and it narrows this a long way.** Two
> inspection folders exist from the failing afternoon, each with a `photos/`
> subfolder that is **empty**, and the recycle bin proves nothing was uploaded
> and later deleted. Since `upload()` runs
> `ensureFolder → tagFolder → drive → transfer`, and the folders and their
> library columns are both present, **the first three steps work on mobile and
> the fourth does not.** Sign-in, tokens, drive resolution, folder creation and
> the column write are all cleared. The fault is inside the file transfer.
>
> That makes **hypothesis 1 much the strongest** — a real phone photo is 2–5 MB
> and anything over 4 MB takes the chunked path — and makes **hypothesis 3
> unlikely**, since a token good enough to create folders seconds earlier was not
> what failed. It does **not** pick between the livelock and the unreadable blob;
> both live inside that fourth step. See `docs/DECISION-LOG.md`.

**1. The chunked upload path has never run against real Graph.**
Every successful test used a small file — the desktop verification used a
~165 KB canvas image, and the live test used PNG screenshots. `ds-sharepoint.js`
switches to `createUploadSession` above **4 MB**. A real phone photo is 2–5 MB and
a HEIC burst is larger. **The resumable path is only proven against a fake
transport.** Look here first.

> **A livelock was found here in v1.3.2 (D31).** Graph answers a chunk it did not
> commit with a 202 pointing back at bytes already sent; the loop obeyed that
> without checking for progress, so the file could be re-sent for ever — every
> request succeeding, every deadline met, nothing finishing. **This matches the
> field report most closely of anything found so far.** Fixed, plus a whole-file
> deadline. Still needs the device to confirm it was the cause.

**2. Blobs in IndexedDB on iOS.** Safari has a history of stored blobs becoming
unreadable after a reload. If `originalOf(rec)` returns an invalid blob, the fetch
may hang rather than fail. Test by reading a stored blob's `size` and slicing it
before upload.

> **Addressed in v1.3.2 (D33).** `DSMedia.verifyReadable()` reads a 64 KB slice
> and checks the size before the upload starts, so a dead blob fails by name
> instead of stalling inside `fetch` — where a request-body stall is invisible to
> a response deadline. `diagnostics.html` §2 reads every stored photo back.

**3. Token refresh in a standalone PWA.** iOS treats an installed PWA as a
separate storage context. Sign-in was confirmed working, but a *refresh* on an
expired token in standalone mode is a different path and untested.

> **A real gap was found here in v1.3.2, and it was in the v1.3.1 fix.** Token
> requests had no deadline at all, and `getToken()` is awaited *before* a request
> is issued — so it sat outside the deadline B6 added. A hung sign-in server hung
> the upload with nothing sent. Now bounded in both places (D32), and a timeout
> no longer signs the device out. `diagnostics.html` §3 can force the refresh
> path on demand.

**4. `crypto.subtle` at capture.** Requires a secure context — fine on the live
HTTPS site, would fail silently on plain HTTP. Only relevant if testing locally.

> **Ruled out in v1.3.2 without a device.** `sha256Hex()` already returns null
> when `crypto.subtle` is absent and catches its own failures, so a non-secure
> context cannot hang capture. Struck off.

**Instrument before fixing.** The absence of diagnostics is itself B6.

> **The instruments are now in place (v1.3.1).** Hypothesis 1 gains direct
> support from the timeout work: the chunked path is the one request that could
> previously hang forever with nothing on screen. Reproduce on a real device with
> a real phone photo and read the per-file status — a timeout on the chunk PUT
> confirms hypothesis 1; an immediate failure with a readable reason points
> elsewhere. Note that hypothesis 2 (blobs in IndexedDB on iOS) would now surface
> as a failure rather than a hang, since a stalled read can no longer wait
> indefinitely.

## 4. The architectural change — SharePoint as the transfer point

**Today** the baton moves as a file the user shares by hand. **That is the design
fault.** On mobile there is no sensible target, so the baton cannot be passed at
all.

**Change:** *Share draft* uploads the `.json` to the inspection's `current/`
folder through Graph — the same transport photos already use — and moves the
previous file to `archive/`. *Import draft* lists what is in `current/` and pulls
it down. The share sheet remains only as an offline fallback.

We already have the transport, the auth, the folder structure and the naming. The
work is wiring, plus a list/download capability on the transport.

### What this unlocks

- **Rollback.** `archive/` already holds every prior handover. If a device is
  lost, corrupted, or someone leaves without closing out, the last version is
  recoverable. Today it is not, because the file never left the device.
- **Import from SharePoint** — B8 — falls out of the same change.
- **Automatic backup of in-progress work**, below.

### Automatic backup — the highest-value item on this list

Right now an inspector's in-progress inspection exists **only on their device**
until they deliberately export. A lost phone loses a day of work with no copy
anywhere. That is the largest remaining data risk in the system.

**Proposal:** when signed in and on a connection, the app quietly uploads the
current record's `.json` to `current/` — say every few minutes while editing, and
on returning to the home screen. Cheap: these files are tens of kilobytes.

Two things to decide, and they are genuine questions rather than details:

> **Settled in Batch 3 — `wip/`, and for a mechanical reason (D39).** Every backup
> changes the file's eTag, and the eTag in `current/` is what a handover uses to
> detect a second device. Backing up there would fire that warning on the
> owner's own saves until it was ignored. The second question below is answered
> by naming the file per device.

- **Does an auto-backup break "one baton, never a copy"?** Argument that it does
  not: it writes only to the folder that already belongs to that stage's owner,
  and it is that person's own working copy. But it does mean `current/` changes
  without a deliberate handover, which the protocol currently promises.
  **A separate `wip/` folder may be the honest answer** — a working copy, clearly
  not the baton.
- **What happens when two devices hold the same inspection?** Today the import
  path warns and offers a fork. Automatic writes need the same protection, or
  they will silently overwrite.

chat, including about superseded versions. The source already exists — the guides
and the decision log — so the question is only how to publish them into a
SharePoint location Copilot indexes, **without manual copy-and-paste**.

the Site Inspections site. Note the same principle as D23: set it at write time,
do not reconcile later. `tools/make_guides.py` already produces the artefacts, so
this is a publish step rather than new authoring.

future version. Sensible, and it becomes far more valuable once several apps exist.
Consider where reports land — a SharePoint list is the obvious answer and matches
the existing direction.
