# v1.3 Development Record

**Point-in-time record of the v1.3 development cycle.** Written for loading into
the Claude Project *2.1 — DS Leaking Basement Site Assessment Form* so a future
session starts with the state and the traps rather than rediscovering both.

**Deployed:** 17 August 2026 · App v1.3.0 · Form 4.2 · schema 4
**Scale:** 34 commits, 37 files, ~10,400 lines added
**Live:** https://ds-js1.github.io/dryspace-inspect/

---

## 1. Where things stand

The app is live and verified, running on GitHub Pages from `main`. Photos upload
to a dedicated SharePoint site with read-back verification, staff sign in with
their Dryspace Microsoft account, and the app announces its own updates.

Before this cycle the live app had been on **v1.1.1 since 20 July**. v1.2.0 and
v1.2.1 were both completed and never deployed — the photo-persistence problem made
the app unusable in practice, so work went straight to v1.3. Field devices
therefore migrate **schema 1 → 4 in a single pass**, covered by tests against the
real v1.1.1 build.

---

## 2. What v1.3 delivered

**Photos reach SharePoint.** Three renditions per photo — a 240px thumbnail for
previews, a 1600px copy that keeps emailed reports deliverable, and the untouched
original as evidence. The original uploads to
`Site Inspections ▸ INS-2026-0142 - Smith - 12 Marine Parade, Kirra ▸ photos/`.

**Nothing is deleted on trust.** Every upload is confirmed by an *independent
read-back* of the stored file, not by the upload response — which can report
success on a truncated write. `"All photos uploaded"` only appears after that
check passes.

**Sign-in.** OAuth 2.0 authorization code with PKCE, hand-written rather than
MSAL: ~150 lines against ~200KB, in an app whose defining property is being
self-contained. No client secret exists anywhere, which is what makes the client
and tenant ids safe in a public repository.

**Updates announce themselves.** The service worker waits rather than
self-activating; the home screen shows a banner. This is how v1.1.1 stayed live
unnoticed for a month.

**Permanent media ids.** `data-mfid` on every file input — the one place v1.2's
`data-fid` work had been skipped.

**One folder per inspection**, holding `current/`, `archive/` and `photos/`,
indexed by six SharePoint library columns written at upload time. Filenames carry
a pinned client token so a file separated from its folder still identifies itself.

**A test suite.** 241 assertions running the real functions through an iframe, so
they cannot drift from shipping code. Migration coverage is proven against the
actual v1.1.1 build, not a synthetic record.

**Governance that loads itself.** `CLAUDE.md` is read at the start of every
session; `05_Release Protocol.md` tiers the work; `docs/DECISION-LOG.md` records
what was decided and why, including reversed decisions.

**Documentation and training** rebuilt for v1.3 and made self-contained, so v1.0,
v1.1 and v1.2.1 can be superseded.

## 3. What was found — the useful part

Nine real defects, listed because each one describes a class of mistake rather
than a one-off.

| # | Found | Why it matters |
|---|---|---|
| 1 | **The live app was v1.1.1.** Two finished versions had never been deployed | Nothing ever checked that live matched intent. Now step 6 of the release protocol fetches the served file and confirms `APP_VER` moved |
| 2 | **B4** — the retired "Basement construction type" dropdown had 6 options and `VALUE_RULES` converted 5. Choosing "Other" converted to nothing | `assignKeys()` accepted only one legacy rule per control. Found by the test harness on its first run |
| 3 | **Media keyed by the file input's DOM id** | Renaming an id orphaned every photo attached to it — the exact fragility `data-fid` was created to remove |
| 4 | **A transient network error stranded a photo permanently.** `failed → uploading` is not a legal transition, so the retry threw out of the drain loop after one attempt | Found by running the queue against a fake transport |
| 5 | **Fixing #4 exposed a second bug**: permanent errors (400/403) were retried to the cap, because "move on" re-entered the loop with the record still eligible | The first bug's crash had been masking it |
| 6 | **The test harness tested stale code, twice.** The app re-registered a service worker inside the test iframe and `clients.claim()` took over the page; separately the modules were served from the browser's HTTP cache | It reported an already-fixed bug as still broken. A suite that can silently grade yesterday's code is worse than none |
| 7 | **The "Upload now" button was unreachable.** The sync bar read the pending count once at start-up and never again | Every layer beneath it was tested and passing. **Nothing asked whether a person could reach it.** Found by using the app |
| 8 | **`APP_VER` was never bumped** — still `1.2.1` while every document said v1.3 | Caught by the guide-freshness check on *its* first run, having survived an entire development cycle |
| 9 | **`folderName()` silently dropped the client name** that Dryspace's own convention included | Found by reading the old Handover Protocol against the new code |

### And one correction to the record

It was asserted here that delegated `Files.ReadWrite.All` requires admin consent
by default. It does not — that is the *application* variant. What actually forces
admin approval is the tenant's user-consent policy for apps without a verified
publisher. Worth knowing if consent behaviour ever looks inconsistent.

## 4. Rules that must not break

Each exists because breaking it lost, or nearly lost, real data. Full list in
`CLAUDE.md`, which loads automatically.

- **Every control needs a permanent `data-fid`**; every file input a `data-mfid`.
  A control without one is silently excluded from saved data — no error, no
  warning, the answer simply never saves.
- **Never reword a radio or checkbox option without a `VALUE_REMAP`.** Answers are
  stored as the option's text. Field ids protect against renaming a *label*, not
  rewording an *option*.
- **Never delete a local original that has not been verified** by independent
  read-back.
- **Never bump `APP_VER` without `CACHE_VERSION`.** A forgotten cache bump is
  silent: the deploy succeeds and every device keeps the old app.
- **Capture is never blocked.** Storage warnings warn; they never prevent a photo
  being taken.
- **Nothing at capture time may require a network call.** There is no signal where
  the data is captured, and that single fact shapes the whole architecture.

## 7. The lesson worth carrying to the sibling apps

Two of the most consequential findings came from **using the app, not testing it**:
the Upload button being unreachable, and the live app having sat on v1.1.1 while
two versions never shipped.

The suite is genuinely strong on the machinery — queue, transport, verification,
retry, migration. It has never once been able to tell whether a person could reach
any of it.

Build the same tests for the progress-inspection app. Then open it and try to use
it, on a real device, before believing it works.
