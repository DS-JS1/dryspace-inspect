Dryspace Site Inspection App — Changelog
========================================
v1.0.0 — 20 July 2026
- Initial release. Built from Site Inspection Form v4 (Project 2.1), all 12
  sections and dynamic reveals preserved.
- Offline-first PWA: installable on iPad / iPhone (Safari) and Android (Chrome).
- Continuous autosave to on-device storage (IndexedDB); suspend/resume;
  edit after completion; multiple concurrent draft inspections.
- Photo compression (~1600px JPEG) with thumbnails; video/document storage;
  per-item remove.
- Send: self-contained HTML report (answers + embedded photos + hidden JSON
  data block for Proposal Builder 3.0) via device share sheet; separate
  "Share photo & video files" for full-size media; all-inspections JSON backup.
- Versioning: bump APP_VER (index.html) and CACHE_VERSION (sw.js) each release.

v1.1.0 — 20 July 2026
- Office pre-fill / handover workflow: "Share draft (handover to field team)"
  button exports a DS_Draft .json; "Import draft / report / backup" button on
  the home screen imports it on any other device. Same-ID imports prompt to
  replace or keep both.
- Reports now embed raw field data (rawData) so a sent report .html can be
  re-imported as an editable inspection on another device.
- Backup files can now be restored via the same Import button.
- Dryspace logo embedded (from logo_DrySpaceSolutions_2025_alone.png) — shown
  in the app header, form header and at the top of every report; works offline.
- Drafts now carry attached files: photos (compressed) and documents/floor
  plans (PDF, images) travel inside the draft .json. Videos are excluded from
  drafts (size) and listed by name — share those via OneDrive. Drafts over
  20 MB prompt before export.
- Version footer on the home screen now reads from APP_VER automatically.
- Bumped APP_VER 1.1.1 / CACHE_VERSION ds-inspect-v1.1.1.
NOTE: backups remain field-data only. Drafts carry photos/documents but not
videos. Reports carry compressed photos; full-size media is shared via
"Share photo & video files".

v1.3.0 — IN DEVELOPMENT
--------------------------------------------------------------------------
Under version control from this release. The app is now developed in a git
repository; every change below is a reviewable commit rather than a folder copy.

Migration and field integrity
- Retired "Basement construction type" dropdown: choosing "Other" now converts.
  assignKeys() previously accepted only ONE legacy rule per control, and the
  merged Other checkbox already carried one, so that answer had no path across.
  Rules are now ";;" separated. Found by the new test harness, not by review.
- Media is keyed by a permanent data-mfid instead of the file input's DOM id.
  Renaming an input's id previously orphaned every photo attached to it — the
  one place v1.2's stable-id work had been skipped. Existing media is rekeyed
  automatically at start-up and after a draft import.

App updates are now visible
- The service worker no longer activates a new build silently. It waits, and
  the home screen shows "A new version of the app is ready" with an Update now
  button. Previously updates applied without notice, on the browser's own
  schedule — and an installed iOS PWA that is never fully closed may not check
  for weeks. This is how v1.1.1 stayed live while two versions sat finished.
- New "Check for app update" button on the home screen for checking on demand.
  Reports the running version and states plainly when there is no connection —
  in a basement that is expected, not an error.
- Updating refuses while an inspection is open, since applying one reloads the
  app. Only offered from the home screen.

Test harness (new)
- tests.html: 76 assertions run against the real functions inside index.html via
  a hidden iframe, so they cannot drift from shipping code.
- Migration coverage is proven against the actual v1.1.1 build rather than a
  synthetic record: all 296 keys it can produce are accounted for — 294 mapped
  to a stable id, 1 merged, 1 converted by value rule.
- Release gates: CACHE_VERSION must carry APP_VER (a forgotten bump is silent
  and leaves every device on the old app), the field id manifest must exist and
  agree, and the changelog must carry an entry for the current version.

Media handling (v1.3, in progress)
- New ds-media-sync.js: capture, naming, integrity and upload queueing, written
  standalone so the planned job-update and silica-worksheet PWAs reuse it rather
  than copying it.
- Photos now keep THREE copies: a 240px thumbnail for previews, a 1600px copy so
  emailed reports stay deliverable, and the untouched original as the evidence
  copy. Video and PDFs keep one copy.
- "Share photo & video files" now genuinely shares the originals. Before v1.3 it
  shared the 1600px copies while describing itself as full-size media.
- Every original is fingerprinted (SHA-256) when it is captured.
- Uploads are verified by reading the stored file back and comparing its size,
  never by trusting the upload response — which can report success on a
  truncated write. Nothing on the device becomes safe to delete without that.
- Storage warnings appear as originals accumulate, but capture is never blocked.
  Running out of space is recoverable; an un-photographed defect is not.
- Upload itself is not yet connected — that needs the Entra app registration.

Filenames now identify the job (v1.3)
- Photos and handover files carry a short client token, so a file that has been
  downloaded, emailed or dropped into Teams still says whose job it is:
    INS-2026-0142_Smith_2026-08-15_s4-wall-moisture-signs_001.jpg
    DS_Draft_INS-2026-0142_Smith_S02-FIELD_2026-08-15T1430_JS.json
  Previously the inspection number was the only identifier, which meant looking
  it up before you knew whose photos you were holding.
- The token is PINNED on first use. Photos uploaded before the office fills in
  the client name would otherwise be named differently from photos uploaded
  after, for the same job. A later correction to the name does not rename
  earlier files.
- The client name is used rather than the suburb because it is a real field.
  A suburb would have to be parsed out of the free-text address, and
  "Unit 3/12 Marine Pde Kirra QLD 4225" has no reliable separator.
- Capped at 24 characters so a long body-corporate name cannot run away.

Inspections are indexed by SharePoint library columns (v1.3)
- The app writes InspectionNo, Client, Address, Stage, InspectionDate and
  LastEditor onto each inspection folder, so the folder list is a sortable,
  searchable index with nothing to generate and nothing that can drift.
- Writing the index never blocks an upload. If the columns are missing or the
  write is refused, the photograph is still stored.

Fixed before release (v1.3.0)
- The "Upload now" button never appeared. The sync bar read the number of
  waiting photos once at start-up and never again, so after attaching a photo it
  still said "No photos yet" and offered nothing to press. It now refreshes when
  a photo is attached, when one is removed, and on returning to the home screen.
  Found by using the app, not by the tests - the upload logic underneath was

Printed guides are now generated, not hand-made

  the version from APP_VER so the filenames always match what tests.html checks.
  Bump the version, re-run it, and the release gate goes green.

v1.3.1 — 18 August 2026
Batch 0 of the v1.4 plan. Two upload faults found by field testing on iPhone and
iPad, fixed and shipped on their own rather than held behind the architecture
work. Nothing about how a photo is captured, named or stored has changed.

Interrupted uploads no longer strand a photo (B5)
- An upload killed by the app being closed, backgrounded or reloaded left its
  record in the 'uploading' state for good. Nothing counted it: pendingUploads()
  did not, and neither did the queue. The photo silently never uploaded, the
  "Upload now" button disappeared, and nothing on screen said why. This is the
  cause of "the Upload now button disappears and I cannot get it back".
- DSMedia.recoverInterrupted() now returns every such record to 'queued' at
  start-up, before the queue is built, so nothing can be draining while stranded
  records are moved. After a reload nothing can still be in flight, so a record
  found in 'uploading' was interrupted by definition.
- 'uploading' -> 'queued' is deliberately still illegal in the transition table.
  Widening it would legalise a record moving backwards mid-drain, which would
  mean two attempts against one file. Recovery bypasses the table instead, and
  says so.
- A file that has already used its attempts is marked failed and flagged for
  attention rather than returned to a queue that would skip it — that would be
  the same invisibility by another route.

Requests now have a deadline, and failures are readable (B6)
- Nothing in the Graph transport could time out. A hung request left the app on
  "Uploading…" indefinitely, with nothing to read and no way out.
- Every request now carries an abort deadline: 60s for metadata, folder creation
  and verification, 180s for an upload. The chunked-upload PUT gets its own,
  because it bypasses call() and is the request most likely to stall on a phone.
- A timeout is classified as temporary, so the queue retries it rather than
  holding the file back as permanently broken.
- The sync bar now lists every file that has not landed yet, with its state,
  upload percentage while in flight, and the actual reason when one fails. A
  stalled upload was previously indistinguishable from a slow one.
- "Upload stopped" now names the file it stopped on and, for a timeout, says the
  connection stalled rather than reporting a bare error string.

Also
- Guides regenerated as v1.3.1; superseded v1.3.0 PDFs removed. Field id
  manifest reissued for the new version — the field set itself is unchanged.
- Training/ was not reviewed. The per-file status panel is a visible change and
  would normally force that review, but this build is development-only and the
  training pack updates as a set at v1.4. Recorded as D28 in the decision log.


v1.3.2 — 18 August 2026
Batch 1 of the v1.4 plan, in the only form possible without the failing device:
the four hypotheses in the plan's §3 were hunted by reading rather than by
reproduction, and a diagnostic was built so the device can answer the question
itself. Three independent ways for an upload to hang for ever were found and
closed. NONE OF THEM IS CONFIRMED AS THE MOBILE FAULT — each is a real defect
that could produce the reported symptom, and the real cause is still unproven.

The chunked upload could livelock (hypothesis 1)
- Graph answers a chunk it did not commit with a 202 whose nextExpectedRanges
  points back at bytes already sent. The loop obeyed that answer without
  checking whether it advanced, so the file could be re-sent for ever: every
  request succeeding well inside its deadline, the file never finishing, the app
  showing "Uploading…" indefinitely.
- This is exactly the class of fault the plan predicted for this path, and it
  survived every test because a fake transport always advances.
- Now: progress is required. Re-sending a chunk once or twice is legitimate;
  three non-advancing answers stops the attempt with the byte offset in the
  message. It is retryable, because a new attempt opens a new session, which is
  the actual remedy.
- Also added a whole-file deadline (15 minutes). Per-chunk deadlines cannot
  bound a session that keeps answering promptly but never gets anywhere.

The token request had no deadline, and sat outside the one added in v1.3.1
- getToken() is awaited before a request is issued, so it was outside the
  request deadline added in v1.3.1. A sign-in server that never answered hung
  the upload before anything was sent — the earliest and least visible stall in
  the chain, and a hole in the v1.3.1 fix.
- ds-auth.js now has its own 30s deadline on token requests, and the transport
  has a backstop for any token source that does not.
- A timed-out refresh is temporary: the device is NOT signed out and the refresh
  token is NOT discarded. Only a rejection from the server does that.

Stored files are read before they are sent (hypothesis 2)
- Safari can return a blob from IndexedDB that stored fine and reads back
  broken. Handed to fetch() as a request body, a stall there is invisible to any
  deadline waiting on a response.
- DSMedia.verifyReadable() now reads a 64 KB slice, and checks the size against
  what the record expects, before the upload starts. An unreadable file fails by
  name and is held for attention — retrying cannot restore a lost blob, and the
  only real remedy is to retake the photo.
- A read that merely times out is treated as temporary instead.

Hypothesis 4 ruled out by reading
- crypto.subtle is already guarded: sha256Hex() returns null when it is absent
  and catches its own failures. A non-secure context cannot hang capture. This
  hypothesis can be struck off without a device.

New: diagnostics.html
- Run it on the device that fails. It reports the environment, reads every
  stored photo back, times getToken() and can force the refresh path, resolves
  the library, and uploads a file you pick from the camera roll through the real
  chunked path — with a timed trace of every Graph request.
- It names the hypothesis when one is confirmed.
- It loads the app in an iframe rather than copying its configuration, for the
  same reason the test suite does (D22).
- It uploads to _diagnostics/ and deletes nothing, because staff accounts may be
  Contribute - No Delete.
- Running it unregisters the service worker for the site. The page says so.

Tests
- 307 assertions, up from 284. The new ones prove the livelock is detected and
  bounded, the whole-file deadline fires, a hung token no longer hangs an
  upload, a device stays signed in through a token timeout, and an unreadable
  file is never sent.


v1.4.0 — 18 August 2026
PATCH FOLDED IN, same evening — a stranded upload found on the beta build.
APP_VER stays 1.4.0 because 1.4.0 has not been released; CACHE_VERSION moved to
ds-inspect-v1.4.0-2 so installed test devices actually take the corrected build.

The fault, from the device: two photos sat as "Uploading" for ever with no
progress and no error, while the app said "All photos uploaded" above them.
Diagnostics ruled out the usual causes — both blobs read back in 6ms and 2ms,
getToken() in 377ms, the library resolved in 735ms. A reload turned both rows
into "Waiting", which proved the uploading state had never been written.

- An IndexedDB transaction that ABORTS fires onabort, not onerror. tx() handled
  only onerror, so an aborted write never settled and the queue's save(rec)
  never returned — leaving the record in 'uploading' with nothing in flight.
  This is B5's shape one layer further down. onabort is now handled, on reads
  as well as writes: a hung read strands start-up recovery, and then no upload
  queue is built at all.
- Every storage call now has a 15s deadline, covering the ways a transaction
  can go quiet that no handler can see — including openDB() blocking behind
  another tab. A storage error is recoverable; a storage call that never
  returns is not.
- The summary counters now count 'uploading'. The sync banner says "N file(s)
  uploading now" and the inspection card says "N uploading", instead of both
  claiming completion over a panel that says otherwise.
- The banner still opened with "All photos uploaded" when files were stuck
  (failed and non-retryable) - caught on the device by the very screenshot
  that was meant to confirm the first fix. Completion is now claimed only
  when nothing is outstanding at all. CACHE_VERSION -> ds-inspect-v1.4.0-3.
- STILL HUNG after all of the above, on a device where the diagnostics page
  had just proved the transport working on the same 5.24 MB photo: 2 chunks,
  verified, 10.5s. So the fault is in driving the transport, not in it.
  Bounding more things was not the answer - being able to see where it
  stopped was. An attempt now reports the step it is on, and a watchdog
  fails it after 60s without progress naming that step, so the record ends
  as a readable failure that can be retried instead of a frozen row.
- refreshSyncDetail() no longer ends in an empty catch. It draws the upload
  percentage, so when it failed the panel silently stopped repainting and a
  frozen row looked like a stalled upload. That cost a whole round trip.
- diagnostics.html: usedSession was declared below its own uses, so it read
  as undefined and the page always announced "simple PUT - under 4 MB", in
  red, while running a chunked session. It reported the opposite of what it
  was doing.
- ROOT CAUSE, found the first time the instrumentation ran: "Failed - the
  stored file could not be read back: The object can not be found here."
  The original was stored as the File handed over by the camera, which is a
  reference to a file iOS owns, not bytes this app holds. iOS reclaims that
  temporary file and the record survives pointing at nothing. The report
  copy was always fine because canvas produced it, so the app owned it.
  Captured files are now read once into an ArrayBuffer and rebuilt as a
  Blob, so IndexedDB holds real bytes. Same storage, held properly. A
  failed read keeps the File rather than dropping the photo.
- "Take over an inspection from SharePoint" never worked. Scanning starts by
  listing the library root, and listFolder built root::/children for the
  empty path, which Graph rejects with 400 "Resource not found for the
  segment 'root:'". Listing the root is a different URL shape - which
  createFolder already knew and listFolder did not. Found by the owner
  clicking the button out of curiosity; it had never been exercised end to
  end against real Graph, only against mocks that answered the path form.
- 417 assertions, up from 387. CACHE_VERSION -> ds-inspect-v1.4.0-6.

The architectural change: the record now travels the same road as the photos,
and in-progress work is backed up without anyone having to remember to do it.

owner's decision: the form, the field ids, the photos and the workflow are all
unchanged, and every planning document already calls this work v1.4.

The baton moves through SharePoint (B7, B8)
- "Hand over through SharePoint" uploads the record to the inspection's current/
  folder and moves the previous file into archive/. Steps 3 and 4 of the handover
  ritual, which were manual and on a phone were impossible.
- "Take over an inspection from SharePoint" lists every inspection with a file
  waiting in current/ and brings the chosen one down. The baton could previously
  be put down but not picked up.
- The share sheet survives as an explicitly labelled offline fallback, on both
  sides. It is the right tool with no signal and the wrong one otherwise.
- Photos are not embedded in a draft that goes through SharePoint — they are
  already in photos/ beside it. The offline fallback still embeds them, because
  there the draft is all the receiver gets.

Two devices holding one inspection
- The record now carries a baton pointer: the identity and eTag of the current/
  file this device last agreed with. Schema 3 -> 4, with a migration.
- On handover the app compares it with what is actually in current/. If someone
  else has handed over in the meantime it names them, says when, and asks. It
  never silently overwrites.
- Two files in current/ is refused outright and sent to Handover Protocol §8.
  Which one is the baton is not a decision software should make.
- The pointer is written the moment the upload lands, before the archive move is
  attempted — so a device that hits a permissions error on the move does not
  then believe someone else has handed over.

Order of operations, chosen deliberately
- Upload the new file BEFORE archiving the old one. Archiving first would leave
  current/ empty if the upload then failed, and the protocol has no procedure for
  an empty current/ — it reads as lost data to whoever opens the folder. Two
  files in current/ is also wrong, but §8 already says exactly what to do about
  it, and the filenames carry timestamps so the newer is obvious. Fail into the
  error the protocol knows how to handle.

Transport
- list, download, move and putSmall added to ds-sharepoint.js. All carry the
  deadlines added in v1.3.1/v1.3.2.
- A move is a re-parent, so the item id survives and links already handed out
  still resolve (D9). It is also not a delete, which matters where field accounts
  are Contribute - No Delete.
- A folder that does not exist yet lists as empty rather than throwing. An
  inspection nobody has handed over has an empty in-tray, not a fault.
- A draft is tens of kilobytes and goes by simple PUT, not a chunked session.

Documentation
- 03_Handover and Version Control Protocol §4 rewritten: the ritual is now four
  steps, with the manual version kept as the no-signal path.

Tests
- 335 assertions, up from 308. The four handover scenarios were also driven
  end to end against a stubbed transport in the running app: empty current/,
  a clean handover with archiving, a second device detected and cancelled,
  two files refused, and an archive move failing after a successful upload.


Batch 3 — automatic backup of work in progress
Until now an in-progress inspection existed only on one device until somebody
deliberately handed it over. A lost phone lost a day's work with no copy
anywhere. That was the largest remaining data risk in the system.

- The app now quietly uploads the current record to the inspection's wip/ folder
  every four minutes while editing, and once on leaving the form.
- "Recover work in progress" on the home screen lists what has been backed up
  and brings a copy down. A backup nobody can restore from is not a backup.

It writes to wip/, not current/
- The v1.4 plan left this genuinely open. What settles it is mechanical rather
  than philosophical: every backup changes the file's eTag, and the eTag in
  current/ is exactly what a handover uses to tell "nobody has touched this"
  from "somebody else has handed over" (D35). Backing up into current/ would
  make that warning fire on the owner's own saves — constantly, and therefore
  ignored.
- It also keeps the protocol's promise that current/ changes only at a
  deliberate handover.

Two devices on one inspection — the plan's second open question
- One backup file per DEVICE, not per person: a person may carry two, and
  per-device naming means two devices working the same inspection cannot
  overwrite each other's backup. Answered by the naming rather than by locking.

A working copy is not the baton, and says so everywhere
- Its own docType, so the baton import will not accept it.
- Its own folder, which nothing listing the baton looks in.
- Its own control, worded to send you to the handover path if that is what you
  actually wanted.
- Recovering one clears the baton pointer, because this device has not agreed
  with anything in current/ — so the next handover will say so and ask.

It never gets in the way
- Silent in every failure case: signed out, offline, photos using the
  connection, or nothing identifying the record yet. A failed backup is not an
  inspector's problem to solve mid-inspection, and saying so would train them to
  ignore real warnings.
- Leaving the form does not wait on it.

Fixed: saving undid the migration
- saveNow() pinned cur.schema to a literal 3. The moment the schema moved to 4,
  every record would migrate on load and be written straight back as 3 — for
  ever, silently, undoing the migration that had just run. Found while wiring
  the backup. ensureSchema() now owns that number and saveNow only preserves it.

  .then() was landing after the summary had been printed, and a late failure
  nobody counts is worse than no test.

Filing-critical fields are checked once, at handover
- Five fields decide how a record files rather than what it says: inspection
  number, client, address, inspection date, and the name of whoever is handing
  it on. They name the folder, pin into every photo filename, and become the
  library columns.
- Deliberately NOT enforced at the field. A blank field mid-inspection is
  legitimate, and permanent warnings train people to stop seeing warnings.
  Capture is never blocked (D16); this is that principle one level up.
- The handover asks once, names each blank field and what it decides, and shows
  the folder the record will file as. OK hands over anyway. It asks; it does not
  block.
- It runs before anything is listed, moved or written, so cancelling leaves
  SharePoint exactly as it was.
- It tells the truth about pinning: once photos have uploaded the folder is
  fixed, so filling the number in afterwards corrects the record and the columns
