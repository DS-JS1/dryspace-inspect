Upload diagnostics

Run this on the device that fails. Sections 1–6 answer the four hypotheses in docs/v1.4-plan.md §3 in order and tell you which one is actually true. Sections 7 and 8 answer the two faults the baton test found on 21 August 2026 — the library columns the app cannot read, and the storage that is not being reclaimed. Nothing on this page writes to the app, the database, or the record.

It must be opened from the app's own web address — the same https://… URL you open the inspection app from. Not from SharePoint, not from a file on the device, and nothing to do with an email address.

It has to share an origin with the app because it loads the app in a frame, reads the same stored sign-in, and opens the same database. Served from anywhere else, none of those resolve and the page cannot do its job.

One side effect worth knowing. This page loads the app with ?nosw=1 so it cannot test a stale cached build — which unregisters the offline service worker for this whole site. When you have finished, open the app normally once and let it load; it re-registers itself. Do not leave a field device in this state, because until you do, the app will not work without signal.

This page can be served stale to itself. The service worker caches whatever it is asked for, including this file, and it ignores the query string — so ?v=2 will not force a fresh copy. If the sections below stop at 6, you are reading an old copy: the load you just did unregistered the worker, so simply open this page once more and section 7 will appear.

5 · The chunked upload — hypothesis 1

The decisive test. Anything over 4 MB goes through createUploadSession, and that path has only ever run against a fake transport.

Pick something over 5 MB — a short video is ideal. Chunks are 5 MiB, so a file under that is sent as a single chunk and never exercises the part where a session can stall between chunks. A 10–20 second phone video is 20–50 MB and gives four to ten chunks, which is the real test. A typical still photo is 2–4 MB and will take the simple path instead, proving nothing about this hypothesis.

Leave it empty to use a synthetic 5 MB file, which reaches the session path but only just.

6 · What the app has actually stored

The panel on the home screen draws what it thinks is happening. This reads the database directly and reports what is really there — one row per photo, with the state the upload queue sees. If the screen and this disagree, the screen is wrong. Nothing here changes anything.

Two readings are shown. Loading this page boots the app in a hidden frame, and the app's start-up recovery moves anything left in uploading back to the queue — so the state worth seeing is gone by the time you tap. The first reading is taken before that happens.

7 · Can the app read the library columns?

The baton lives in two library columns — BatonStatus and BatonHolder. On 21 August 2026 the library showed both set on a folder while the app, reading that same folder at that same moment, saw neither. That was proved here on 22 August and fixed: the listing asked for $select on a nested navigation property, which names it without populating it, so Graph returned a listItem carrying nothing but an etag.

The section now earns its keep as a regression check. Three readings of the same library root: the app's own listing code, which cannot drift from what the app really does; the old broken form, kept as a control that should still come back empty; and the documented form. A healthy result is the app and the documented form agreeing, with the control blind.

Only top-level folders carry the baton, so the library root is what gets listed — the same listing the take-over picker uses. Name a folder below and its raw response is printed in full; leave it empty and the first folder found is used. Name one you know has a holder set, or a blank column proves nothing.

8 · Where has the storage gone?

A device reporting 140 MB in use with no inspections on it is either holding something it should have released, or the figure does not mean what it looks like it means. This measures every store directly instead of guessing.

Read the caveats before drawing a conclusion. The headline figure covers the whole origin, which hosts the live app at the root and the beta together, so some of it may not belong to the build under test — the cache rows below name which build each cache came from. A browser is also entitled to hold on to deleted data for a while before reclaiming it, and cross-origin cached files are padded in the quota accounting and measure as zero here. An unattributed remainder is a lead, not a verdict.

The cache figures are captured before this page boots the app, because booting it carries ?nosw=1, and that deletes every cache on the origin — the offline copies of both the live app and the beta. That is the existing behaviour of the flag, not something this section does, but it means the caches can only be counted once per visit and they are counted for you on the way in. If a reading looks wrong, reload the page and take it again rather than tapping twice.

Read-only apart from that: this section deletes nothing, sweeps nothing and tidies nothing.

Delete the database — empty devices only. On 22 August 2026 this device reported ~140 MB held while every store was empty, and iOS Settings agreed, so the space is real rather than a misread figure. The leading explanation is that WebKit keeps IndexedDB in a file that does not shrink when records are deleted — the container stays big after the contents go. Deleting the whole DATABASE removes the file rather than emptying it, so if that is the explanation, this reclaims the space and the figure falls. If it does not fall, the explanation is wrong and the space is somewhere else.

This destroys every inspection, photo and byte record on the device.
